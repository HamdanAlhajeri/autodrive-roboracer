# September 21 milestone

## Project purpose

Build our own AVLite plugins for autonomous racing across different tracks, including mapping, localization, planning, and control. Use the simulator as the vehicle during development, then transfer to a real RoboRacer/F1TENTH car using LiDAR, IMU, and encoders. Start with solo timed laps and a slow mapping run before faster racing.

## A. Consistent fast driving

Prioritize the current practice track. Work toward 5 m/s on suitable straights with automatic slowing for corners. A configured speed alone does not demonstrate success: measure actual speed and repeatability.

- Capture the current baseline, including crashes, lap times, actual speed, steering, throttle saturation, sensor age, and controller timing.
- Investigate the fixed 1 m lookahead and corner speed first. Develop speed-dependent lookahead and limit speed using curvature, clearance, and measured braking response.
- Measure throttle and braking response; tune AVLite acceleration and the actuator loop together so corner deceleration promptly reduces throttle.
- Preserve watchdogs and correct units; do not loosen timeouts to hide problems.
- Record target velocity, lookahead, clearance, and saturation alongside the existing telemetry.
- Screen speed targets from 2.5 to 5 m/s in 0.5 m/s increments, requiring three clean laps before advancing. Run the full repeatability check on the final profile.
- Save each run's configuration and data. Keep the fastest passing profile and explicitly document any remaining failure at 5 m/s.

Acceptance: **three fresh runs, each with ten consecutive clean laps**, with zero collisions, resets, or manual intervention during the measured run. Report actual straight-line speed, lap-time variation, and sensor interruptions.

## B. Start mapping and localization offline

Build a reference map and our own initial localizer without making the live racing controller depend on them this week.

- Extend recording with an optional raw sensor capture mode for LiDAR, IMU, encoders, transforms, controls, and reference poses. Keep lightweight graph recording available.
- Implement a 2D occupancy-grid mapper using LiDAR and simulator ground-truth poses initially. Ray-trace free and occupied cells, preserve unknown space, and save map resolution and frame information.
- Implement 2D ICP scan-to-map localization, initialized by one supplied pose, with encoder and IMU yaw-rate prediction. Do not use ground-truth position or orientation for subsequent localization updates.
- Reject poor scan matches and report failures explicitly; do not silently fall back to ground truth.
- Keep algorithm cores independent of ROS and structure integration around AVLite's mapping and localization strategy interfaces.
- Provide offline map-building and localization-evaluation commands. Evaluate on a separate recording and export estimated/reference trajectories, pose-error graphs, failure counts, and processing times.

Acceptance: a saved reference map and a repeatable offline localization evaluation, with tests for known scan transforms, invalid or missing sensors, coordinate frames, and replay. Document measured accuracy. This is a reference-assisted prototype; autonomous SLAM and live estimated localization remain later milestones.

## Scope and stretch work

The existing practice track is required. Keep ground-truth localization in the live driving baseline while developing the offline prototype.

Importing the user's new `.obj` track is stretch work. Inspect scale, geometry, collision surfaces, and availability of a compatible editable Unity project once the file is provided. Proceed only if it does not delay the driving milestone.

Real hardware deployment, opponents, loop closure, and live estimated localization are outside the September 21 acceptance criteria.
